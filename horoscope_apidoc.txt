================================================================================
HOROSCOPE / ASTROLOGY API DOCUMENTATION
================================================================================
Base URL: /api/v1
Astrology Base: /api/v1/astrology/
Profile Base (birth text + coordinates): /api/v1/profile/  and  PATCH /api/v1/astrology/birth-coordinates/

Architecture (current):
- Horoscope **calculation** is performed by a **Windows desktop EXE** at the client office. The EXE reads
  `horoscope_profile` input columns and writes output columns (`pr_rasi`, `pr_star`, etc.) directly to MySQL.
- Django **stores and serves** that row via `HoroscopeProfile` and runs **porutham** in Python using EXE data
  (`pr_star`, `pr_pada`, `pr_rasi`). There is **no** Swiss Ephemeris generation, **no** `grahanila` JSON, and **no**
  server-side chart PNG or chart JSON from planet longitudes.

Authentication:
- Member endpoints: `Authorization: Bearer <access_token>` unless noted.
- `Content-Type: application/json` for POST/PATCH with JSON bodies.

Response envelope (member JSON APIs):
- Success: `{ "success": true, "data": { ... } }` or `{ "success": true, "message": "..." }`
- Error: `{ "success": false, "error": { "code": <http_status_int>, "message": "..." } }`

--------------------------------------------------------------------------------
0) SUBSCRIPTION (ACTIVE PLAN) AND HOROSCOPE MATCH QUOTA
--------------------------------------------------------------------------------
"Active plan" follows the same rules as elsewhere (`plans.services` / `get_user_plan_status`).

Without an active plan, a member may still:
- GET/PATCH profile birth-related APIs as documented in profiles (e.g. birth-details).
- GET `/api/v1/astrology/horoscope/me/` — own `HoroscopeProfile` row (no plan gate).
- PATCH `/api/v1/astrology/birth-coordinates/` — own profile coordinates.

With an **active plan**, these additionally apply:
- GET `/api/v1/astrology/horoscope/<user_uuid>/` — another member’s public horoscope summary (see §3).
- POST `/api/v1/astrology/porutham/` — compatibility check (consumes quota on success).

Horoscope match quota (`Plan.horoscope_match_limit`; `0` = unlimited):
- **POST `/api/v1/astrology/porutham/`** — each successful **200** consumes **one** unit on `UserPlan.horoscope_used`
  (`consume_horoscope_match`).
- There is **no** `POST /astrology/generate/` anymore; quota is **not** consumed by chart or PDF download stubs.

HTTP 403:
- **No/expired plan** where required: `plan_expired_response`-style payload.
- **Quota exhausted** on porutham: `horoscope_quota_exhausted_response`.

Remaining count: exposed in plan summary as **horoscope_remaining** (same as rest of app).

--------------------------------------------------------------------------------
1) BIRTH DETAILS API (PROFILE — TEXT FIELDS)
--------------------------------------------------------------------------------
Birth **time** and **place** (free text) continue to live on `UserProfile` and are updated via the **profiles**
API (see main `apidoc.txt` — `GET/POST /api/v1/profile/birth-details/` or equivalent profile section).

Signals:
- Saving `UserProfile` syncs **input** fields on `HoroscopeProfile` for the same user (`pr_tob`, `pr_lat`,
  `pr_lon`, `pr_name`, `pr_dob` from user/profile). EXE output columns (`pr_rasi`, `pr_star`, …) are **not**
  overwritten by that sync.
- When birth inputs change, `HoroscopeProfile.is_calculated` may be cleared so admin workflows can re-run
  `mark_horoscope_done` after EXE output is refreshed.

**Latitude / longitude** for EXE input are **not** parsed from `place_of_birth` text in Django. Use:

--------------------------------------------------------------------------------
1b) PATCH BIRTH COORDINATES (LAT / LON FOR EXE)
--------------------------------------------------------------------------------
Endpoint: `PATCH /api/v1/astrology/birth-coordinates/`
Auth: Required (JWT).

Request body:
```json
{
  "latitude": 9.9312,
  "longitude": 76.2673
}
```

Validation:
- Both must be finite numbers.
- Latitude in [-90, 90], longitude in [-180, 180].

Success 200:
```json
{
  "success": true,
  "data": { "latitude": 9.9312, "longitude": 76.2673 }
}
```

Errors:
- **400** — invalid or out-of-range coordinates (envelope above).

Side effect:
- Updates `UserProfile.birth_latitude` / `birth_longitude` and triggers sync to `HoroscopeProfile.pr_lat` /
  `pr_lon`.

2) GET MY HOROSCOPE PROFILE (CURRENT USER)
--------------------------------------------------------------------------------
Endpoint: `GET /api/v1/astrology/horoscope/me/`
Auth: Required (JWT). **No active plan required.**

Description:
- Returns the logged-in user’s **`HoroscopeProfile`** row as JSON (EXE inputs + outputs + derived fields when
  `mark_horoscope_done` has run).

If no row exists yet:
```json
{
  "success": true,
  "data": {
    "exists": false,
    "is_calculated": false
  }
}
```

If a row exists (typical success):
```json
{
  "success": true,
  "data": {
    "id": 1,
    "pr_name": "...",
    "pr_dob": "1995-02-10",
    "pr_tob": "08:45:00",
    "pr_lat": 9.9312,
    "pr_lon": 76.2673,
    "pr_tz": 5.5,
    "pr_rasi": "ABCDEFGHIJK",
    "pr_amsa": "",
    "pr_bhav": "",
    "pr_star": 5,
    "pr_pada": 2,
    "pr_dasabalance": null,
    "lagnam": "Medam",
    "rasi_sign": "Midhunam",
    "star_name": "Mrigasira",
    "nakshatra_pada": 2,
    "gana": "Deva",
    "yoni": "Sarpa",
    "rajju": "Padam",
    "is_calculated": true,
    "calculated_at": "2026-05-14T10:00:00Z",
    "created_at": "...",
    "updated_at": "...",
    "star_display": "Mrigasira",
    "dasa_display": "06y 08m 25d",
    "lagnam_display": "Medam",
    "rasi_display": "Midhunam",
    "charts": {
      "rasi":  { "lagna_sign": 1, "houses": { "1": [...], "...": [], "12": [] }, "planets": [...], "sign_names": {...} },
      "amsa":  { "...": "..." },
      "bhava": { "...": "..." },
      "star":  { "number": 5, "name": "Mrigasira", "pada": 2 },
      "dasa":  { "lord": "Mars", "balance_days": 2459, "years": 6, "months": 8, "days": 25, "balance_text": "06y 08m 25d" }
    }
  }
}
```

Field notes:
- **`pr_rasi`** / **`pr_amsa`** / **`pr_bhav`**: 11 characters, each character **A–L** maps to zodiac sign **1–12**
  (EXE convention). Position = planet (1=Lagnam, 2=Sun, 3=Moon, 4=Mars, 5=Mercury, 6=Jupiter, 7=Venus, 8=Saturn,
  9=Rahu, 10=Ketu, 11=Maandi).
- **`pr_star`**: nakshatra index **1–27** (see server `astrology.porutham.STAR_NAMES` order).
- **`pr_pada`**: **1–4**.
- **`pr_dasabalance`**: sishta dasa balance in **days** from EXE (optional).
- Derived string fields (`lagnam`, `rasi_sign`, `star_name`, `gana`, `yoni`, `rajju`, `nakshatra_pada`) are filled
  by management command `mark_horoscope_done` after EXE has written outputs. They are **stored** columns and stay
  blank until the command (or admin **sync** endpoint, §7) runs for that row.
  - **`gana`**: `Deva` | `Manusha` | `Asura` (full label, from the client star tables).
  - **`yoni`**: full Sanskrit yoni name (e.g. `Mushika`, `Sarpa`, `Ashwa`).
  - **`rajju`**: `Padam` | `Kanda` | `Udara` (from the client star table).
- **`*_display`** fields are **computed on read** (do not require the command to have run):
  - **`star_display`** / **`lagnam_display`** / **`rasi_display`**: echo the stored `star_name` / `lagnam` /
    `rasi_sign` (blank until `mark_horoscope_done` runs).
  - **`dasa_display`**: always derived live from `pr_dasabalance` using **365-day years and 365/12-day months**
    (e.g. `2459 → "06y 08m 25d"`, matching the Windows EXE panel). `""` when `pr_dasabalance` is null.
- **`charts`**: computed **on read** directly from the raw EXE strings (`pr_rasi` / `pr_amsa` / `pr_bhav`) plus
  `pr_star` and `pr_dasabalance`. This is always correct even when the stored derived columns are still blank.
  Each chart object exposes `lagna_sign`, `houses` (sign-number 1–12 → planet list), `planets`, and `sign_names`;
  `star` and `dasa` carry the nakshatra and Vimshottari balance metadata.

**Removed:** `chart_url`, query param `style`, lazy server generation, and any `grahanila` payload.

--------------------------------------------------------------------------------
Endpoint: `GET /api/v1/astrology/horoscope/<user_uuid>/`
Auth: Required (JWT). **Active plan required** (403 if expired/inactive).

Path:
- **`<user_uuid>`** — `accounts.User.id` (**UUID**), not `UserProfile.id`.

Success 200:
```json
{
  "success": true,
  "data": {
    "pr_rasi": "ABCDEFGHIJK",
    "pr_star": 5,
    "pr_pada": 2,
    "pr_dasabalance": null,
    "lagnam": "Medam",
    "rasi_sign": "Midhunam",
    "star_name": "Mrigasira",
    "nakshatra_pada": 2,
    "gana": "Deva",
    "yoni": "Sarpa",
    "rajju": "Padam",
    "is_calculated": true,
    "calculated_at": "2026-05-14T10:00:00Z",
    "star_display": "Mrigasira",
    "dasa_display": "06y 08m 25d",
    "lagnam_display": "Medam",
    "rasi_display": "Midhunam",
    "charts": { "rasi": {...}, "amsa": {...}, "bhava": {...}, "star": {...}, "dasa": {...} }
  }
}
```

This is the **public** serializer: **no** `pr_lat`, `pr_lon`, `pr_tob`, `pr_dob`, or internal `id` / timestamps

`charts` fields described in §2 (both computed on read).

Errors:
- **403** — plan not active.
- **404** — `HoroscopeProfile` missing for that user id.

**Removed:** `GET /api/v1/astrology/horoscope/<profile_id>/` (integer **UserProfile** pk).

4) PORUTHAM CHECK API
--------------------------------------------------------------------------------
Endpoint: `POST /api/v1/astrology/porutham/`
Auth: Required (JWT). **Active plan required.** Quota consumed on **200** only.

Description:
- Loads `HoroscopeProfile` for the **user** linked to each **UserProfile** id.
- Requires EXE to have written outputs: `pr_rasi` non-empty and `pr_star` set (`is_exe_done()` on both sides).
- Computes Kerala Dashakoot using **`astrology.porutham.calculate_porutham`** (VB-ported logic).
- Upserts **`PoruthamResult`** for the `(bride_user, groom_user)` pair (user FKs, not profile FKs).

Request body:
```json
{
  "bride_id": 101,
  "groom_id": 205
}
```

- **`bride_id`** / **`groom_id`**: **`UserProfile`** primary keys (integers), unchanged from the previous API.

Success 200 — **`data`** is a **single flat object** (not wrapped in `PoruthamResultSerializer` only):

- **Grade integers** (1 = Uthamam, 2 = Madhyamam, 3 = Adhamam, 4 = Neecham) for:
  `dinam`, `ganam`, `mahendra`, `sthree_deerga`, `yoni`, `rasi`, `rasyadhipam`, `vasyam`, `rajju_dosham`, `vedha_dosham`
- **`chovva_dosham`**: boolean or `null` if charts insufficient.
- **`bride_papatha`**, **`groom_papatha`**: floats.
- **`papa_samyam`**: boolean. `true` (favourable) when `groom_papatha >= bride_papatha`
  (bride does not carry the heavier affliction).
- **`dasa_sandhi`**: boolean (VB `dsandhipor` port). `true` (favourable / safe) when there is
  **no** dasa sandhi: the engine builds both partners' Vimshottari mahadasha timelines from
  `pr_star`, `pr_dob` and the sishta balance `pr_dasabalance`, then scans the next 70 years; if any
  bride/groom dasha-change dates fall within 365 days of each other it is a sandhi (`false`). Also
  persisted on `PoruthamResult`.
- **`dosha_checks`**: ready-to-render array for the "Dosha & Compatibility" UI block. Each item is
  `{ "key", "label", "matched" }` where `matched` is a boolean, so the frontend can show a
  tick (`true`) / cross (`false`) exactly like the porutham rows (Vedha / Rajju / Rasi).
  Currently: `chovva_dosham` (Chovva Dosham), `papa_samyam` (Papa Samyam), `dasa_sandhi` (Dasa Sandhi).
  `true` = favourable in every case.
- **Counts:** `uthamam_count`, `madhyamam_count`, `adhamam_count`, `total_porutham_count`
- **`has_dosha`**: boolean summary flag (also set when `papa_samyam` or `dasa_sandhi` fails).
- **`overall_result`**: string such as `Excellent` | `Good` | `Average` | `Not Recommended`.
  `max_score` stays **10**; a failing `papa_samyam` and/or `dasa_sandhi` each demote the grade by one tier.
- **Backward-compatible keys:**
  - **`poruthams`**: object with the **10** keys above mapped to **boolean** (`true` = that koota is Uthamam only).
  - **`score`**: float, equals **`uthamam_count`**
  - **`max_score`**: `10.0`
  - **`result`**: same as **`overall_result`**

**Removed from response:** `koota_points` (0 / 0.5 / 1 Prokerala-style table), old key names `dina` /
`rasi_adhipathi` / `vedha` / `rajju` as separate float scores.

Errors:
- **400** — profile not found; missing `HoroscopeProfile`; EXE not done (`Horoscope not yet calculated…`).
- **403** — no active plan or quota exhausted.
- **404** — `UserProfile` row missing for an id.

5) PAID JATHAKAM / THALAKURI PDF (RAZORPAY) — ORDER & VERIFY
--------------------------------------------------------------------------------
Env (server):
- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` — required for order/verify (503 if missing).
- `ASTROLOGY_JATHAKAM_PRICE_INR` (default 175), `ASTROLOGY_THALAKURI_PRICE_INR` (default 20).

Flow (unchanged intent):
1) **POST** `/api/v1/astrology/pdf/order/`  
   Body: `{ "product": "jathakam" | "thalakuri" }`  
   Success: Razorpay order fields + `price_inr`, `product`, etc.

2) Client completes Razorpay Checkout; client receives `razorpay_payment_id`, `razorpay_order_id`, `razorpay_signature`.

3) **POST** `/api/v1/astrology/pdf/verify/`  
   Body:
   ```json
   {
     "product": "jathakam" | "thalakuri",
     "razorpay_order_id": "...",
     "razorpay_payment_id": "...",
     "razorpay_signature": "..."
   }
   ```  
   Success: `credited`, `already_verified`, `product`, `credit_id`, **`download_url`** (absolute URL with
   `sig` + `credit_id` query params for the product path).

4) **GET** `/api/v1/astrology/pdf/jathakam/` or **`/api/v1/astrology/pdf/thalakuri/`**

**Current behavior (upgrade period):** both endpoints respond with **HTTP 503** and JSON (no PDF body), e.g.:
```json
{
  "success": false,
  "error": {
    "code": 503,
    "message": "Jathakam PDF temporarily unavailable during system upgrade."
  }
}
```
(Thalakuri uses an equivalent message naming that product.)

- Auth class: **`AllowAny`** (so old clients opening a bookmarked URL do not get 401), but the response is still
  **503** until PDF generation is rebuilt for `HoroscopeProfile` / EXE data.
- **Credits are not consumed** on 503 download — purchase/verify flow still creates `AstrologyPdfCredit` rows.

7) ADMIN / STAFF / BRANCH HOROSCOPE PANEL (JWT)
--------------------------------------------------------------------------------
Bases (same relative paths; scope differs by role):
- Admin: `/api/v1/admin/horoscope/`
- Staff: `/api/v1/staff/horoscope/`
- Branch: `/api/v1/branch/horoscope/`

Endpoints:
- **GET** `summary/` — KPI counts from `HoroscopeProfile` + `UserPlan.horoscope_used` (no mangal computation).
- **GET** `records/?search=&branch_id=&page=&page_size=` — list rows. **`jathagam`** status is one of:
  - **`calculated`** — `is_calculated = true` (derived fields filled).
  - **`pending`** — EXE wrote `pr_rasi` but `is_calculated = false` ("Pending sync"; run the sync endpoint/command).
  - **`awaiting_exe`** — `pr_rasi` empty (EXE has not written outputs yet).
- **GET** `records/<user_uuid>/` — detail: `{ "record": {...}, "horoscope": <HoroscopeProfileSerializer|null> }`
- **GET** `records/by-matri/<matri_id>/` — same as detail, keyed by matri id.
- **POST** `porutham/` — body: `{ "bride_profile_id": <int>, "groom_profile_id": <int> }`  
  Success **`data`**: `bride_horoscope` and `groom_horoscope` are **full** `HoroscopeProfile` JSON objects
  (admin serializer), plus the same flat porutham keys as member **§4** (`dinam`, `poruthams`, `score`, …).  
  **Removed from panel porutham payload:** `bride_chart_url`, `groom_chart_url`, `flags`, `koota_points`, grahanila.
- **POST** `sync/` — fills derived fields for all **in-scope** profiles where EXE wrote `pr_rasi` but
  `is_calculated = false` (server-side equivalent of `mark_horoscope_done`, scoped to the caller's role). No body.
  Success **`data`**: `{ "processed": <int>, "errors": <int> }`. Also sets `UserProfile.has_horoscope = true` for
  each processed member. This is the admin "sync / re-fill derived fields" button.
- **GET** `jathakam-pdfs/` — recent Jathakam PDF credits list for users in scope.

--------------------------------------------------------------------------------
8) OPERATIONS (SERVER COMMANDS)
--------------------------------------------------------------------------------
After members have complete birth data and coordinates, and before/after EXE runs:

- `python manage.py push_to_exe_bridge` — pushes `UserProfile` + `User` birth fields into `horoscope_profile`
  for rows that have DOB, time, lat, lon.
- `python manage.py mark_horoscope_done` — for rows with `pr_rasi` set and `is_calculated=false`, fills derived
  labels (`lagnam`, `rasi_sign`, `star_name`, `nakshatra_pada`, `gana`, `yoni`, `rajju`) from the client star
  tables, sets `is_calculated=true` + `calculated_at=now()`, and sets `UserProfile.has_horoscope=true`.

Note: the Windows EXE writes `pr_*` columns **directly to MySQL**, outside the Django ORM, so no `post_save`
signal fires on EXE writes. Derived columns are populated only by `mark_horoscope_done` or the admin **`sync/`**
endpoint (§7). The chart display and `*_display` / `charts` API fields are computed live from the raw `pr_*`
columns, so they render correctly even before the derived columns are filled.

--------------------------------------------------------------------------------
9) WINDOWS EXE ↔ DATABASE (CLIENT CONFIG SUMMARY)
--------------------------------------------------------------------------------
Table: **`horoscope_profile`** (flat; no join required for EXE).

Typical column mapping: `id`, `pr_name`, `pr_dob`, `pr_tob`, `pr_lat`, `pr_lon`, `pr_tz`, and outputs
`pr_rasi`, `pr_amsa`, `pr_bhav`, `pr_star`, `pr_pada`, `pr_dasabalance`.

Use the **same** MySQL database name, host, and credentials as Django.

--------------------------------------------------------------------------------
10) DATA CONTRACT NOTES FOR INTEGRATORS
--------------------------------------------------------------------------------
- Prefer **`GET /horoscope/me/`** for the logged-in user’s full bridge row; use **`GET /horoscope/<user_uuid>/`**
  for another member’s **redacted** summary when the viewer has an active plan.
- Porutham UI should use **integer grades** and/or **`poruthams`** booleans; do not assume **`koota_points`**.
- Chart PNG, chart JSON, match PDF, and server-side `generate` are **out of scope** until redesigned for EXE data.
